# Approved Secret record status: technical implementation

Authority: effective SSOT §8.3 and §25.6, plus `audit/OWNER_SECRET_ROOT_STATUS_DECISION.json`. The owner decision is approved; this document proposes its physical implementation, not another product choice.

`secret-record-status.sql` preserves immutable version lifecycle and bytes. The root status is a read-only materialized projection: `DELETED` when deletion is present, otherwise `ACTIVE` only for one valid same-root same-type ACTIVE version selected by the active pointer, otherwise `INACTIVE` when no active pointer or ACTIVE version exists. Integrity validation precedes deletion presentation, so deletion cannot conceal a foreign, missing, duplicate, or contradictory pointer. New create/import roots must be INACTIVE with no active pointer and no deletion marker.

The controlled migration validates existing relations and updates status alone. It does not rewrite legacy RAW values, ciphertext, immutable provenance, version lifecycle, identity or pointers. Root writers project the value within their transaction. Deferred closure validates the final projection without taking a new root lock after audit-head locking. Client status edits fail; status is not authorization or an editable lifecycle.

Public read interface: `kcml_secret_v1.record_status_v1(uuid) RETURNS text`. Read callers must already hold their required root lock. Missing root produces `SECRET_STATUS_RECORD_UNAVAILABLE`; invalid pointer identity, unavailable pointer, wrong lifecycle, duplicate ACTIVE versions, ACTIVE without pointer, and stale persisted projection produce distinct integrity diagnostics. Reserved OWNER API authorization additionally requires this root projection to be ACTIVE under its held credential-root lock; a deleted credential must not remain authorized solely because its historical version is ACTIVE.

Mask proposal: root/entity/read status enum INACTIVE|ACTIVE|DELETED, server-produced and read-only; create successful output should expose `recordStatus` with const INACTIVE, separate from immutable version `versionState=CREATED` and command envelope `status=SUCCEEDED`. The coordinator must update receipt mask, canonical semantic-result producer and SQL projection together if adding this output field. This owned candidate does not silently modify shared masks.

Actual PostgreSQL 18.6 fixture `verify_status_pg.py`: 22 PASS, 0 FAIL. Source and exact consumed canonical/candidate hashes are in `status-postgres-tests.json`. The proof covers migration preserving immutable RAW, activation, rotation projection, deactivation, deletion, replay read, precise corruption diagnostics and concurrent projection visibility. It does not prove complete activation commands, credential rotation, broker authorization, systemd key authority or application runtime. Initial pending-trigger/DDL and trigger-record-field invocation errors were diagnosed and corrected before the current successful execution; they were not counted as successful tests.

Integration prerequisites: canonical Secret physical roots and reserved role installation from the Secret command/context block. The getter does not repair corrupted reads. Full command/root/event/audit linkage remains the caller operation's independent obligation.
