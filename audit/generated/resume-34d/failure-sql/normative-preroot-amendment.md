### Accepted generation command before root

This technical clarification implements §12.48, §25.11, §49.3–5, §49.25 and §51.12/51.25. It creates no additional product event or trust authority.

Before acceptance, malformed JSON, invalid authentication and rejected admission produce the current `HttpCreateFailure` with `logicalOperationId=null`. They create no command, prospective job, protected snapshot, job root or created event. Authentication/input diagnostics are not transformed into durable accepted command outcomes.

After acceptance, the server reserves the immutable command/job/snapshot identities and freezes exact trusted descriptor, caller request/key digests and protected arguments. A reserved prospective job UUID is not a persisted job. `generation_create_preroot_snapshot` retains the protected arguments independently of a generation_job FK so a known failure can be retained without inventing a job. The trusted context and all identities belong to the authenticated server producer.

The retained outcome is exact current native semantic response bytes (all response members except `resultDigest` and `idempotencyReplay`). It is immutable per command state version. SQL identity and SHA joins bind these bytes to the command, original scope/key/request, locator, business-idempotency outcome and versioned audit chain. The existing finite error tuples determine classification, terminality and retry directive. SQL closed-member/type checks and the actual native schema apply together; syntactic JSON alone is insufficient.

* `ACCEPTED` is nonterminal, has no output/error and retains EXECUTING business-idempotency state.
* A retryable positively established transaction rollback uses `CREATE_PERSISTENCE_FAILED / INTERNAL / RETRY_SAME_OPERATION`, remains nonterminal and retains EXECUTING. The failure receipt is persisted only by a separate recovery transaction after positive rollback evidence; transport silence is not that evidence.
* Unestablished commit outcome uses `SIDE_EFFECT_OUTCOME_UNKNOWN / UNKNOWN / RECONCILE_THEN_RETRY`, remains nonterminal and retains WAITING_FOR_RECONCILIATION. Reconciliation queries the same original operation and locator, never creates a second root.
* Terminal failure retains FAILED_FINAL. Cancellation retains CANCELLED_FINAL only where cancellation won before commit. A committed success is replayed and cannot be recast as cancellation or failure.

Every accepted-before-root retained stage commits command/context/protected input/stage outcome/locator/idempotency/audit together. No generation root, `generation.job.created` event or event-delivery outbox is generated on this path. This does not remove required command audit: its audit event has an exact deferred typed reference to the retained command outcome, uses existing hash format, actor/object/correlation identity and hash-chain locking. Its object is the logical command, not an absent generation root. If the actual pinned archive policy requires it, archive outbox is part of the same commit. Unattached audit rows without a domain event are forbidden.

Command identity/frozen descriptor/argument identity is never replaced on retry. State-version changes advance exactly by one under expected-version CAS. Each retained stage is immutable; a new stage appends a new result/audit and advances the same command. Pending-to-success creates the previously reserved job and native request snapshot with identical schema/content/profile/ciphertext/nonce/key fields, uses the existing successful-create binding and atomic event/outbox/audit completion. Earlier pending stages remain immutable history. Mismatched transfer fails `GENERATION_PREROOT_SNAPSHOT_TRANSFER_MISMATCH`.

Stable-locator lookup authenticates current result access first, acquires the original locator/scope locks and compares the caller request digest. Same digest returns the original frozen outcome or latest durably persisted nonterminal stage; different digest returns existing IDEMPOTENCY_CONFLICT. Current contract/deployment/target changes do not recompute the retained descriptor or create a second job. Evidence of missing/purged retained details follows the existing §49.4 tombstone rules rather than manufacturing a result.
