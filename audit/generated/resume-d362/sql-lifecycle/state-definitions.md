### Own operation response state dictionaries — technical materialization

This materializes technical receipt vocabulary under §12.18. It does not change actor privileges, fixture scope, business behavior or derive an enum from a similarly named entity. Authoritative source pointers are the four effective operation-overlay records located by operationId, §21.3 (enrollment), §11.24 (canonical central chat), §25.14 and §29.5 (acceptance), §49.4–49.5 (canonical outcome and atomic audit/outbox).

* `owner.mfa.reset.enrollmentState = ENROLLMENT_REQUIRED`: successful reset's immutable **as-committed postcondition**, not a query of current factor progress. Reset increments the MFA reset epoch once, invalidates old factors/recovery material and creates a bounded fresh enrollment challenge in its transaction. A verified new enrollment, challenge expiry or renewal does not rewrite this successful command's retained receipt. Reset does not attest that the session has completed fresh MFA. The separate enrollment lifecycle/read contract remains distinct.
* `chat.turn.steer.checkpointDisposition = STEERING_COMMITTED`: successful command's immutable **as-committed instruction/intent receipt**. The instruction is durably ordered and bound to the exact conversation, turn and predecessor checkpoint; its successor-checkpoint reservation or interrupt intent is persisted with it in the same audit/outbox transaction. This value deliberately attests neither completed interruption nor cancellation of any child effect, and does not permit authority replacement, turn restart or a new implicit turn. Terminal/stale turn fails the existing conflict admission predicate; replay returns the retained command outcome. Worker consumption and side-effect reconciliation are separate records, not extra values inferred from generation-discussion lifecycle.
* `acceptance.run.start.state = QUEUED`: successful create's immutable **as-committed admission receipt** for the inserted acceptance run and frozen exact release/SHA/profile/test-plan plus queue/outbox reservation. It does not claim that a worker is already running or that acceptance passed. Current run reads use their own lifecycle and must not rewrite the start command's successful receipt.
* `acceptance.run.cancel.state`: own persisted cancellation-stage snapshot, with `CANCEL_REQUESTED` after intent/version commit, `RECONCILING` while known pending fixture cleanup/effect/check reconciliation remains, `MANUAL_REVIEW` when a recorded unresolved/unknown effect or failed cleanup requires manual resolution, and `CANCELLED` only after all closure predicates hold. This is not the full acceptance run lifecycle. While the cancellation command is nonterminal, current operation lookup may return its latest durably persisted stage (§49.4); a terminal cancellation outcome is immutable. A terminal successful/failed run cannot be silently recast as cancelled.
* `acceptance.run.cancel.cleanupStatus`: `PENDING` if any required cleanup has no successful closure receipt; `FAILED` if a known failed cleanup receipt remains unresolved; `COMPLETE` only when every required cleanup obligation has an exact successful closure receipt and the orphan inventory is empty. `FAILED` has precedence over `PENDING`; absent inventory never means empty.
* `acceptance.run.cancel.reconciliationStatus`: `UNKNOWN` if any required side effect has unresolved unknown outcome; `MANUAL_REVIEW` if an exact outstanding manual-resolution record exists and no unknown outcome takes precedence; `PENDING` if any required effect/check lacks its terminal closure receipt; otherwise `COMPLETE`. The full inventory must be pinned to the exact run/release/fixture namespace/test-plan digest and verified after the cancellation fence. Empty lists are valid only when the pinned authoritative obligation set is actually empty, never because it was omitted or filtered by a client.

Cancellation closure uses actual immutable inventory entries, not a client count or `valid=true`: exact expected IDs must equal the observed IDs without duplicates; receipts bind run ID, release SHA and plan digest; each cleanup has a typed outcome; each effect has a typed known/unknown outcome; each required check has terminal evidence. Unknown effects, unresolved failed cleanup, pending checks or orphan entries prohibit CANCELLED. All snapshot updates and eventual terminalization require the current run/fence, preserved cancellation intent, and one transaction with the corresponding canonical outcome, audit event and outbox reservation. A stale worker cannot mutate the receipt. Manual resolution uses existing exact OWNER command/evidence rules, never an invented automatic-success conversion.

A missing response field, extra enum value, null or wrong type is invalid. These six exact masks close these six bounded response-field definitions after normative integration. They do not close the four entire operations, their full error/event/transport/UI boundaries, run workers or MFA/central-chat entity lifecycles. Required pre-generation fixtures must still test real persistence/locking/atomicity. Application implementation acceptance remains separate and NOT_EVALUATED.
