### 8.12 Verzované Secret profiles, přesné bytes a load/use předávka

Toto ustanovení zpřesňuje pouze `value` representation v §8.11; ostatní metadata, OWNER authorization, reserved singleton/deployment pravidla, transport a idempotency zůstávají podle svých vlastních kontraktů. Přesná maska je `urn:kcml:secret-profile-handoffs:1#/$defs/SecretCreateBody`. Dosavadní `encoding=UTF8|BASE64` jsou explicitní RAW varianty, nikoli implicitní reprezentace strukturovaných profilů. Klient nesmí prohlásit identity, schema digests, target authority nebo registry review za serverové hodnoty.

Pro devět komplexních typů je novou importní variantou `value.representation=PROFILE_JSON_V1`, povinný explicitní `profileId` a objekt `profile` s odpovídajícím diskriminátorem `variant`. Každý profil má vlastní closed masku bez libovolných fields. Exact `(type,profileId)` jsou OAUTH_CLIENT/OAUTH_CLIENT_SECRET_V1; OAUTH_TOKEN_SET/OAUTH_BEARER_TOKEN_SET_V1; TOTP_SEED/TOTP_BASE32_V1; CERTIFICATE/X509_PEM_CHAIN_V1; PRIVATE_KEY/PKCS8_PEM_PRIVATE_KEY_V1; DATABASE_CREDENTIAL/DATABASE_USER_PASSWORD_V1; COOKIE_JAR/HTTP_COOKIE_JAR_V1; SESSION_STATE/BROWSER_COOKIE_LOCAL_STORAGE_V1; SSH_CREDENTIAL/SSH_PASSWORD_V1 nebo SSH_OPENSSH_PRIVATE_KEY_V1. Jsou to omezené profily pro přesně deklarované konzumenty, nikoli univerzální formáty celého typu.

Server před persistencí použije strict UTF8 JSON parser, odmítne duplicitní klíče, nonfinite čísla, chybné kódování, missing/extra fields, nesprávný type/profile/variant a skutečnou type-specific parser chybu. Nepoužije sniffing, trim, case/Unicode normalizaci, PEM rewrite, implicitní token decode ani převod RAW JSON textu na profile. Citlivá hodnota se neobjevuje v diagnostice; error obsahuje přesný stable code, relativní field pointer a pevnou bezpečnou zprávu.

RAW UTF8 a BASE64 si zachovávají přesné dosavadní masky. Šest opaque typů používá RAW; nový komplexní import vyžaduje PROFILE a neověřený legacy raw policy je `SECRET_PROFILE_REQUIRED`, nikoli automatická konverze. Dříve uložená RAW verze zůstává byteově a typově zachována. Převod existující verze je explicitní autorizovaná tvorba nové immutable verze; čtení či reveal nedělají migration in-place.

Pro PROFILE je plaintext přesný původní UTF8 JSON span `value.profile`, včetně původních escapes a whitespace. Server zachová tyto bytes pod authenticated encryption podle §8.4 a §50.30. Persistovaná metadata jsou exact Secret/version identity, type, `value_representation`, nullable profile/schema identity a digest (null iff RAW), `payload_format=EXACT_SECRET_BYTES_V1`, plaintext byte length, original import bytes digest a samostatný type-specific canonical value digest. Identity, metadata a crypto fields jsou immutable podle §25.6/51.20. Create vytvoří CREATED candidate bez active pointeru a bez consumer bindingu.

`original_import_bytes_digest` je SHA256 původních plaintext bytes. `canonical_value_digest` má explicitní preimage `UTF8("KCML_SECRET_VALUE_V1") || NUL || UTF8(type) || NUL || UTF8(value_representation) || NUL || UTF8(profileId or "RAW") || NUL || canonical_payload`. Pro RAW je canonical_payload přesně plaintext bytes. Pro PROFILE je to `KCML_SECRET_PROFILE_CANONICAL_JSON_V1`: validovaný closed profile, keys lexikograficky tříděné, UTF8 bez ASCII escaping, kompaktní JSON se separators comma/colon, přesné decimal integer a standardní JSON escaping stringů, bez nonfinite hodnot. Přímá numeric pole těchto masek jsou integer; IEEE754 browser state se přenáší explicitně jako kódované bytes. Toto není implicitní tvrzení o RFC8785/JCS. Canonical payload slouží pouze digests; nikdy nenahradí uložené original bytes. Schema digest pinne skutečné bytes closed definition bundle; schemaId řetězec sám není důkazem.

Registry publikuje pouze immutable ACTIVE descriptor po skutečném normativním review a požadovaných důkazech. Row obsahuje přesnou type/profile/schema identity, skutečné schema bytes, jejich ověřený digest, autoritativní source digest a review evidence digest. Draft kandidáty jsou mimo ACTIVE registry; neexistuje update měnící význam téhož schema digestu ani mutable CANDIDATE→ACTIVE přepínání stejného descriptoru. Model/client nemohou vložit trusted registry row. Deset omezených parser/import profilů lze aktivovat po přezkumu jejich konkrétních masek a testů; to neuzavírá celý typ, všechny konzumenty ani celou `secret.create`.

Load přijímá exact externě požadované Secret/version IDs z retained broker resolution (§8.8/49.22.1), nikoli jen internally self-consistent row. Ověří selected identity, authenticated crypto metadata, source/schema bytes a digest, type/representation/pinned parser, byte length, original digest a canonical digest. Jiný skutečně autentický ciphertext pod týmž key nesmí nahradit vybranou version. Use deklaruje přesný consumer identity/revision/purpose, compatible type/profile/schema tuples, target binding, algoritmy/parametry a podporované serializers. Unsupported variant nebo member se odmítne konkrétní chybou bez fallbacku. Consumer declaration je serverový pinned contract, ne klientem tvrzená authority.

OAuth token endpoint je autoritativně určen exact target bindingem; případný profilový endpoint je importní deklarace a při use musí souhlasit celý endpoint včetně path/query, client identity a authorized scopes. Pouhá shoda origin/hostname nestačí. DB endpoint/vendor/TLS jsou v bindingu; profilový database údaj musí souhlasit. Outer UI url/username jsou display metadata, nikoli náhradní auth source. Supported key algorithms, RSA parameters/EC curves/DSA sizes a TOTP security/period/clock pravidla deklaruje konkrétní consumer. Parser support ani příznak valid nejsou authorization.

Import kandidáta neprokazuje způsobilost k použití: expired token nebo syntakticky validní neověřený certifikát lze zachovat jako candidate; use ověřuje vlastní expiry/trust/target pravidla a exact current binding. Nové profile masks nemají nedoložené 4096-character/item, 32-chain, seed-ten-byte ani period-300-second universal limity. Zůstává doložený transportní byte limit a skutečná přesná parser/consumer omezení.

Omezený cookie/localStorage profil nikdy nenahrazuje celý browser state bundle z §13.15. Další closed `BROWSER_AUTH_STATE_GRAPH_V1` profile je technické doplnění stejného povinného rozsahu (partitioned cookies, IndexedDB, per-page sessionStorage, permissions, client-certificate metadata a virtual automation WebAuthn); zůstává NOT_ACTIVATED do skutečných engine/serializer/bridge/signature fixtures. Nepodporovaný potřebný member se nesmí vynechat ani označit za budoucí nepovinné rozšíření. Capture/restore barriers, exact account/tenant/epoch postconditions a CAS z §13.15 zůstávají povinné.

Create/import responses a events neechojí citlivé bytes. Explicitní OWNER reveal/copy/export a důvěryhodné business použití z §8.5/8.6.1/8.8 zůstávají podle svého exact auth/transport/audit kontraktu. Syntetická evidence nepoužívá živé účty a nepublikuje citlivé hodnoty. Reference AES-GCM ani parser/SQL fixture nevybírají production master-key/cipher profile ani neprokazují fungující aplikaci.

Exact schema bytes jsou compiled JSONSchema document s `$schema`, `$id`, `$defs` a root `$ref`, nikoli pomocný obal `root/defs` bez schema významu. Registry hash ověřuje právě tyto bytes a jejich root profile. Direct integer JSON tokens se dekódují přesným Decimal parserem: matematicky integral `30`, `30.0` a `3e1` mají stejnou typed integer hodnotu a type-canonical digest; jejich původní plaintext bytes a original-byte digests zůstávají různé. Fractional numerics nepřecházejí na integer zaokrouhlením. NaN/Infinity nejsou validní vstupy.

Root metadata type edit není blanket zakázaný. Inactive record může změnit metadata type a historická version si zachová immutable vlastní type/profile/digest. ACTIVE pointer však musí composite FK `(record.id,record.secret_type,record.active_version_id) → (version.secret_id,version.secret_type,version.id)` dokazovat exact identity i aktuální kind. Metadata edit nesmí přepsat interpretaci již active value. Přechod k jinému active kindu vyžaduje atomickou vlastní activation/retirement/CAS/epoch/invalidation transakci podle §49.22.1/51.20; neprovádí implicitní převod starých bytes. Broker consumer kind používá exact selected version interpretation a musí souhlasit s current active root/binding při use.
