#### 12.51.1 RETRY phase-effect inventory

Pole `FailedTechnicalPhaseRun.pendingSideEffectIds=[]` samo nedokládá reconciliovaný source phase run. RETRY musí atomicky načíst actual `side_effect_operation` řádky pod phase/job foreign keys a přesný immutable inventory snapshot jejich operation/current attempt/current attempt-state/evidence identities a digests. Uzavřené masky `PhaseSideEffectInventory`, `SourceSideEffectOperation`, `SourceSideEffectAttempt`, `SourceSideEffectAttemptState` a `SourceSideEffectOutcomeEvidence` určují konkrétní serverová pole; nejde o klientský body nebo modelové assertions.

Snapshot identifikuje source job, exact phase-run identity/digest, capture time a všechny nalezené operations. Každý operation record se skutečně dekóduje z bytes. Inventory membership musí přesně odpovídat locked phase-FK table scanu; unknown, duplicate, omitted nebo cizí producer identity se odmítá. Samotný row count, `complete=true`, prázdný pending list ani trusted fixture flag scan nenahrazují.

Pro každou operation se ověří immutable source request digest, exact node/side-effect/retry policy, target binding/revision/idempotency key, current attempt identity/sequence, immutable attempt bytes, mutable attempt-state projection a přepočtené digests. Serverový operation/current-state JOIN snapshot obsahuje `currentAttemptStateId` a `currentAttemptStateVersion`; obě hodnoty musí přesně odpovídat skutečné current projection. Nejde o nové klientské údaje ani požadavek na nové physical operation columns. Inventory nesmí vybrat starší, samostatně validní projection téhož attemptu a outcome. §49.8 singleton current state row a jeho version se materializují ve stejném locked scanu; historické snapshoty nejsou autoritou aktuálního stavu. Operation a current-attempt state musí souhlasit podle deferred consistency §49.8. Actual append-only outcome evidence musí patřit přesně této operation/attempt/source phase/request/target binding; její actual observation bytes se validují against exact frozen observation schema a konkrétní deklarovaný server consumer classifier s ověřenými source bytes/digest. Classifier musí vrátit konkrétní známý outcome; obecný validity boolean se nepřijímá. Jde o compiled platform consumer, nikoli execution modelového nebo OWNER-uploaded kódu.

`INTENT_RECORDED`, `DISPATCHING`, `OUTCOME_RECORDED`, `RECONCILING` nebo `UNKNOWN` blokují nové retry dispatchování a vyžadují deklarované reconciliation. `CONFIRMED_APPLIED` se u vybrané neúspěšné části neopakuje. `FAILED_FINAL` se nesmí automaticky reinterpretovat jako bezpečný nový attempt; přesná final-effect policy musí být vyřešená. `CONFIRMED_NOT_APPLIED` dovoluje pouze vlastní další attempt policy pod stejnou operation/target idempotency relation (§49.8), nikdy nové náhodné target key. `NO_AUTOMATIC_RETRY` vyžaduje vlastní explicitní dispatch policy, nikoli tichý fallback. Již dokončené nevybrané části se neopakují. Parent job terminality se z těchto pravidel neodvozuje.

Chybějící mandatory inventory, classifier nebo physical scan evidence jsou BLOCKED. Finite diagnostiky `GENERATION_RETRY_INVENTORY_*`, `GENERATION_RETRY_OPERATION_*`, `GENERATION_RETRY_ATTEMPT_*`, `GENERATION_RETRY_EFFECT_*` a `GENERATION_RETRY_OUTCOME_CLASSIFIER_*` se deklarují jednotlivě; žádný prefix catchall. Whole phase-FK membership, roles/locks, immutable rows, source request and classifier authority a transaction boundaries musí mít skutečný PostgreSQL fixture důkaz. Syntetický ledger a compare-and-set classifier dokazují jen vymezený referenční obsah; nejsou runtime důkazem ani univerzálním consumerem.
